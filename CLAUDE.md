# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

Observatory is a cross-platform desktop app for visualizing disk usage (think DaisyDisk). It's a native Rust app, drawn with [gpui](https://gpui.rs): a parallel filesystem scanner, everything the app knows about what it found, and the window that draws it, as three crates in one Cargo workspace at the repo root.

It used to be an Electron app, with the scanner loaded into Node as a native module. That's gone, and nothing of it is left to keep working: there's no JS in the app, and no build of it that anyone has to be moved off (its updater never shipped).

## Common commands

From the repo root:

- `cargo run -p observatory` — the app. `-- --demo` opens the fake disk, `-- --scan=<path>` (or just a path) scans a folder, and `-- --about` opens the About window too.
- `cargo test` — the unit tests of the scanner and of core, against ephemeral tmp directories. No hardcoded paths.
- `cargo fmt` and `cargo clippy` — what `check.yaml` runs, with `typos` for spelling. On Linux it installs gpui's libraries first, since `cargo` at the root builds the app too.
- `cargo build --release` — the app, and the scanner's CLI (`observatory-scan [--bench] [--perf] <path>`, for ad-hoc scans and benchmarking: JSON to stdout, timing and counts to stderr).
- `macos/build.sh` — packages the app for macOS, Apple silicon only, into `target/macos/`: `Observatory.app` (the release binary without its symbols, `macos/Info.plist` with the version filled in, and the icons from `build-resources/`), a `.dmg` with the app beside a link to Applications, and a `.zip` of the app for the updater. The script is the packaging. It signs ad hoc, or with the team's Developer ID certificate (hardened runtime) when `APPLE_TEAM_ID` is set, and with `APPLE_ID` and `APPLE_APP_SPECIFIC_PASSWORD` too it notarizes and staples both the app and the dmg, the same variables the release workflow has. The version is the desktop crate's.
- `windows/build.ps1` — on Windows, packages the app as an MSIX, for whichever architecture the Rust toolchain is, into `target\windows\`: the release exe, `windows/AppxManifest.xml` with the publisher, version, and architecture filled in, the logos from `build-resources/msix`, and a `resources.pri` so Windows finds their sizes (MakePri, MakeAppx, and SignTool from the Windows SDK). With `WINDOWS_CERTIFICATE` (a base64 .pfx) and `WINDOWS_CERTIFICATE_PASSWORD` it signs the package, and the manifest's publisher is the certificate's subject, which Windows insists on; without them the package is unsigned and named `…-unsigned.msix` (the manifest's publisher has the marker Windows 11 asks of one), so opening it installs nothing but `Add-AppxPackage -AllowUnsigned` (PowerShell, as administrator) does. A package's version is four numbers and has to go up, so a prerelease's number goes in the fourth (alpha.N is N, beta.N 100+N, rc.N 200+N, and the release itself 1000).
- `flatpak/build.sh` — on Linux, builds the Flatpak (`flatpak/ooo.lilac.observatory.yaml`) from the checkout with flatpak-builder and installs it for the user: one `cargo build` on the plain Freedesktop runtime, and the icons from `build-resources/hicolor`. It has `--filesystem=host-root` (Flatpak 1.17+), so the whole host, mounts and all, is at `/run/host/root` in the sandbox. See `flatpak/README.md`.
- `icon/build.sh` — regenerates the app icons (Blender, `uv`, Xcode 26+) and copies what ships (`icon.icns`, `Assets.car` for macOS 26, `icon.ico`, `icon.png`, the MSIX's logos, and the GNOME icon theme) into `build-resources/`. See `icon/README.md`.

gpui's Metal shaders are compiled by the build only when the desktop crate's default `runtime-shaders` feature is off, which needs Xcode's Metal Toolchain (`xcodebuild -downloadComponent MetalToolchain`); `macos/build.sh` turns it off when the toolchain's there, and otherwise the app compiles them each time it starts.

The only JS left is the website's (`site/`, a Vite page with its own `package.json`), and the formatter and linters the root `package.json` has for it and for the repo's Markdown, JSON, and YAML (`pnpm fmt`, `pnpm check.lint`, `pnpm check.health`). Package manager: **pnpm** (`pnpm-lock.yaml` is the source of truth). Node: see `.nvmrc`.

## Architecture

Three crates, each knowing nothing of the one after it:

- `src/scanner/` (`observatory-scan`) — the filesystem traversal, and queries over the tree it builds. A library, and the CLI above.
- `src/core/` (`observatory-core`) — everything the app knows that isn't drawing, so another front end (a TUI, say, with the sunburst over the kitty graphics protocol) can sit on it too: the scans and drive list (`scans.rs`, `drives.rs`, which call the scanner directly and say what changed through a callback), the render tree (`tree.rs`), navigation history, the store (`store.rs`: theme, recents, each scan's cleanup queue, in `settings.json` in the config folder), deleting (`cleanup.rs`), formatting, finders, reserved groups, scan issues, list sorting, the palette and the sunburst's colors (`color.rs`, OKLCH to sRGB), updates, and the fake disk. `sunburst/` is the sunburst without a renderer: `layout.rs` turns a render tree into wedges, `geometry.rs` gives a wedge's outline as polygons (and what's under a point), and `transition.rs` (`Sunburst`) is told which wedges to show and hands back what to draw each frame while it moves from one folder's to the next's. It has no gpui in it and must stay that way.
- `src/desktop/` (the `observatory` binary) — the gpui window. One view, `Workspace` (`workspace.rs`), holds all the state and what changes it; each screen is an `impl Workspace` block in a file named for it (`welcome.rs`, `scanning.rs`, `inspect.rs`, `sunburst.rs`, `lists.rs`, `cleanup.rs`, `issues.rs`, `prompts.rs`), over `chrome.rs` (title bar, toolbar, and the layers over a screen). The sunburst is a `canvas` that fills core's outlines as paths and asks for another frame while anything's moving. `popup.rs` is the one context menu, `menus.rs` the application menu, keys, and actions (handled app-wide, forwarded to the workspace), `text_input.rs` the find field (grown from gpui's `input` example), and `controls.rs` / `palette.rs` / `shapes.rs` the small things. Icons are lucide SVGs in `icons/`, compiled in (`assets.rs`).

Zoom and the scanner's perf flame graph (which the CLI's `--perf` still builds) are left out of the app on purpose.

## The scanner

`src/scanner/` is a synchronous parallel scanner driven by `rayon`'s work-stealing pool: `read_dir` once per directory, then per-entry `metadata` and recursion fanned out through a parallel iterator. No async, no tokio.

A whole disk is millions of nodes, so the `Tree` (`lib.rs`) is kept as small as it can be: a `VfsNode` is 32 bytes, its children a boxed slice, its mtime `u32` seconds, and its name a `u32` symbol for a string kept once in the tree's `Names` (`string-interner`), since names repeat across a disk (only a third of a Mac's are distinct). Nothing draws all of it: `tree.rs` cuts a slice around a folder, where entries smaller than 0.3% of it are dropped from the sunburst and recursion is capped at depth 6, and core's `tree::assemble` turns that into a `RenderTree`. Find (`find.rs`) and removal after a delete go over the tree the same way.

It skips `/dev` and `/proc` on Linux and `/Volumes`, `/System/Volumes`, `/private/var/db/dyld` (plus anything under `/System/Volumes/*`) on macOS to avoid Catalina+ firmlink shadow paths and recursive procfs/sysfs mounts. On Linux, where a scan goes among mounts comes from `/proc/self/mountinfo` (`mounts.rs`, the plan is made once per scan): into every mount of the scanned disk it can reach (btrfs subvolumes, which `st_dev` can't tell apart from other disks), into a folder a bind mount shows only once (at its shallowest place, or where it already was on a tie: an ostree system's `/etc` counts at `/etc`, not in the deployment under `/sysroot`), and not into other filesystems. Nested btrfs subvolumes that aren't mounted are gone into too. An ostree system's `/` with composefs is a read-only image of the deployment, so a scan of it counts only the mounts in it. Without a mount table (Windows), cross-device descent is rejected (never on macOS, because firmlinks break the dev-id check). A file with several hard links (`nlink > 1`, so not on Windows) counts once, at the link whose path sorts first; links that lose out to one found later are zeroed and their folders re-totalled after the walk. Symlinks, character/block devices, and unknowns are counted but not added to the tree. File sizes are allocated space (`st_blocks × 512`), not length, so sparse disk images (Docker, VMs) count what they actually occupy; Windows falls back to length.

Permission errors on folders another account owns, and macOS EPERM refusals outside the home folder (SIP, data vaults), aren't reported as issues: they're locked on every Mac. The scan root's own failure always is. EPERM inside the home folder (Mail, Messages, other apps' containers) is reported with kind `protected`, which the app folds into one issue with an "Open System Settings" button (a deep link to the Full Disk Access pane, `access.rs` in core). Whether the app has Full Disk Access is checked once per scan by trying to list `~/Library/Application Support/com.apple.TCC`; once it does, every remaining EPERM is dropped as expected. In a debug build the grant has to go to whatever launched `cargo run` (the terminal), since macOS attributes the program to it. The first scan asks for it up front, if the app doesn't have it (`prompts.rs`, once, remembered in the store).

Windows' equivalent is administrator rights. When the app isn't elevated and the scan is of this computer's own disk (a network drive is no different for an administrator), Access Denied is reported with kind `admin`, which the app folds into one issue with a "Restart as administrator" button: `relaunch_elevated` in `admin.rs` relaunches the app through UAC (ShellExecuteEx "runas") with `--scan=<path>`, and it quits on a yes. Elevated, the scanner turns on SeBackupPrivilege, so it can list folders whose ACLs leave administrators out too.

What Windows keeps for itself on a whole disk isn't usage the user can clean up. After a scan of a drive root, `reserved.rs` takes `pagefile.sys`, `swapfile.sys`, `hiberfil.sys`, and `System Volume Information` out of the tree (so they're in no list, find, or cleanup) and hands them back as the result's `reserved`. The legend lists them, grouped as "virtual memory", "hibernation", and "system restore" (core's `reserved.rs`), between the files and free space, and the sunburst draws them in gray in the innermost ring.

Cancellation is cooperative: an atomic flag the recursion checks at directory boundaries. In-flight syscalls run to completion, then the recursion unwinds.

`volumes()` (`volumes.rs`) lists the disks and network shares there are to scan, as the OS's file manager would: on macOS the mount table (`getfsstat`) minus `nobrowse` mounts, with DiskArbitration for volume names and to drop disk images; on Linux `/proc/self/mountinfo` (device-backed, minus loop devices, plus SMB/NFS/sshfs), one row per filesystem however many subvolumes and bind mounts it has, without `/boot` and the EFI partition, with udev labels (an ostree system's `/` is listed as the startup disk, with `usage_path` pointing at `/sysroot`, since statfs of its composefs image says nothing about the disk; in a Flatpak, the host's mounts are read from under `/run/host/root` and listed by their path there, unless the sandbox has the same mount at the same place); on Windows the drive letters (`GetDriveTypeW`, volume labels, `WNetGetConnectionW` for mapped shares). Each volume also says whether it's the startup volume, external, or encrypted (macOS: DiskArbitration, with `/` taking its Data volume's encryption, since FileVault leaves the sealed system snapshot alone; Linux: sysfs, a dm-crypt mapping anywhere under the device and a USB bus in its path; Windows: `SystemDrive` and the storage bus type, BitLocker not yet), and a share's server and protocol are parsed out of its mount source. The welcome screen words these as "2 TB encrypted startup disk" or "Pecha – SMB network share". None of it contacts a file server. How full each one is comes from core's `drives.rs` (`statfs` on macOS, whose `statvfs` can't count a big volume; of `usage_path` if there is one), on a thread of its own with only one call per path out at a time, since a vanished server can leave the call hanging.

## The app

Find is how the user looks for what there is to clean up. The field in the toolbar suggests the finders once it's focused (core's `finders.rs`: large files, things untouched for a year, videos, installers, archives, developer files, caches), each with how much it finds below the current folder. Typing narrows them and puts "Names with …" first. Arrows and Enter pick one; Escape closes the suggestions, and a second Escape clears the query. What a query finds takes the place of the list beside the sunburst until it's cleared. Its scope stays the folder it started in while the user opens what it found, so the results don't shift under them. The matching is the scanner's `find.rs`. A match is always the outermost one, since a folder that matches stands for everything in it, and a package (an app, a Photos library) is one item. Version control folders are left alone, nothing in build output counts as a video, archive, installer, or cache, and a folder merely called `cache` is one only where apps keep data (`Library`, `AppData`, a dotfolder). Only the 500 largest come back with paths; the rest are counted.

Cleanup isn't docked anywhere and has no modal: it floats in the window's bottom-left corner (`render_cleanup` in `cleanup.rs`), and there's no button for it in the toolbar. Each scan has a queue of its own (the store keeps them by the scan's path), so cleanup is only there over a scan's results, never on the welcome screen or while scanning, and what's queued from one scan isn't in another's. Things go in from a row's or a wedge's right-click menu ("Move to cleanup"), from what's checked, or by dragging rows and wedges onto it, and whatever's queued, or inside a queued folder, is struck through in the lists and faded in the sunburst. Shut, it's a pill (dashed and saying what it's for while nothing's queued); a drag turns it into somewhere to land ("Drop to clean up"). Open, it's one card that changes: the queue (how much there is to reclaim, a bar with a segment for each thing queued in the color its row has, and the rows, where a click on one goes to the folder it's in), the question of whether to delete and how (with the disk as it would be without them, when they're all on one disk, `drive_of`), the deleting, and how it went. Once the question's answered, `observatory_core::cleanup::delete_files` runs on another thread, says what it's doing a path at a time (`Step`), and starts no more once its `stop` flag is set, and the workspace's `Deletion` follows it: the total counts up and the bar fills in, with a Stop button. The card saying it went well goes away by itself after a few seconds; one where something couldn't be deleted stays and lists it, with "Try again". What's deleted leaves the queues (every scan's, since scans overlap) and the scans' trees as it goes. A deletion is of one scan's queue, and shows only over that scan.

A scan has no status bar: what's checked, and "Move to cleanup", float at the bottom of the list they're checked in, while anything is.

While a scan runs (`scanning.rs`), the screen is the one its results will be, filling in. The scanner keeps a running size for each folder in the scan's root as it walks (`ScanState::tops`, and `loose` for the files in the root itself; the tree is only there at the end), which `Scans::progress` hands on by name, ten times a second. Each folder is a wedge that grows, beside a list of them ("waiting" until the walk comes to one). Of a whole disk the circle is what the disk says is used, so the wedges grow into it and the ring around is a percentage; of a folder there's no total to measure against, so the wedges share the circle by what's been found so far and the ring only turns. For its first two and a half seconds (`HOLD`) a scan of a folder (not of a disk, whose wedges only grow) shows none of that, only the empty places and a count of items, since that's when it would all be jumping about, and a scan that's done by then goes straight to its results. A network share counts as a folder here, since what its storage has used is often mostly other shares'.

For the same reason, the results of a whole-disk scan aren't measured against the disk's size. The sunburst's full turn at the root, and so the legend's free space, is what the scan found plus what the disk said was free when it finished (`measure` in `scans.rs`): whatever else is on the disk (other shares, other volumes, what couldn't be read) is neither the scan's nor free.

What's only for working on the app (loading the fake disk) is behind a button in the title bar (the construction barrier), beside the theme switch, in debug builds only.

The About window (`about.rs`) is the site's hero in small: the render of the observatory on the site's sunset, under star trails turning around the pole. gpui has no radial gradients and can't turn a picture, so the sky isn't layers a compositor moves: `observatory_core::sky` works the whole thing out a pixel at a time (the sunset's gradients, then each star and its trail by where the pixel is around the pole, added up where trails cross, fading into the horizon and behind the words). `Sky::new` does everything that doesn't turn once; `frame(turns, order)` is a picture of it, which the window asks for about ten times a second on a background thread and swaps in as an image under the scene (`build-resources/about/scene.webp`, cropped from the site's by `site/scene/about.py`, compiled in) and the words. It reads where the horizon, the sun and the pole fall on the render from the `scene.json` beside it. `cargo run --release -p observatory-core --example sky -- sky.bmp [turns]` writes a frame to look at.

Over the sky it lists the version, the installation, the system, and the architecture (`environment()` in `menus.rs`, which Help → Report an Issue fills into a new issue too). The version has the commit it was built from after it, "1.2.0 (53410bd)" or "(53410bd, modified)": `src/desktop/build.rs` stamps it in as `OBSERVATORY_COMMIT`, from git or else from a gitignored `.commit` at the top of the repo, for a build from a copy of the source with no `.git`. Installation is how the copy got there and nothing else (not how it's signed): "Development" for a debug build, and otherwise "App" on macOS, "Microsoft Store" or "MSIX" on Windows (running as a package: the Store's, or one installed by hand, which `GetStagedPackageOrigin` tells apart), "Flatpak" on Linux, or "Portable" for the bare program on any of them. The system is `observatory_core::system`'s: "macOS 26.1" (from `SystemVersion.plist`), "Windows 11 (10.0.26100)" (`RtlGetVersion`, 11 from build 22000 on), and on Linux `NAME` and `VERSION_ID` from os-release ("Fedora Linux 42"; the host's, in a Flatpak), with `PRETTY_NAME` only for a distribution that has no version, since it says too much on some and too little on others.

The typeface is Inter, compiled in so it's the same on every platform (`fonts.rs`, with the `ss01` / `cv05` / `cv11` alternates). gpui picks a weight from among a family's faces and can't ask a variable font for one, so `src/desktop/fonts/` has Inter 4.1's static files, one per weight anything is set in (light, for the About window, and regular, medium, semibold); a new weight needs its file added. The workspace's root sets the font, and so does anything drawn apart from it (the About window, tooltips, the drag preview).

The window has one bar at the top, the app's, never that and the system's, and it says what the OS has for the window's title (`Workspace::title`, "Users — Local Disk — Observatory"). On macOS and Windows it's the title bar (`render_title_bar` in `chrome.rs`) over the toolbar; `window_frame.rs` is what makes it one off macOS. On Windows the system's bar is hidden (`appears_transparent`), and ours draws the menus from `app_menus()` and the window's own buttons (minimize, maximize or restore, close), marked up with `WindowControlArea`s, so Windows still does the dragging, snapping, and the buttons' presses itself. On Linux (`HEADER_BAR`) there's no title bar of the app's: the toolbar is the one bar, as a GNOME app's header bar is, with the update button and a ☰ button (the primary menu, which has the theme switch in it, `primary_menu()` in `menus.rs`, also on F10) at its end. The windows ask to decorate themselves (`WindowDecorations::Client`), and GNOME never decorates a window itself, so there the app does it all: a press on the bar moves the window (a double one maximizes it, the right button brings up the window menu), the buttons are GNOME's round ones, on the sides and in the order of the desktop's `button-layout` (read from the desktop portal and followed as it changes, `follow_button_layout`, into the `ButtonLayout` global), and the window is drawn as GNOME's are (`Frame`), with round corners and a shadow along whatever edges it isn't tiled against: gpui is told the shadow's there (`set_client_inset`), the window's drawn inside it, and a press on it resizes the window (`resize_edge`, caught before anything under the pointer gets the press). Whatever's drawn out to a corner over the rest (a modal's scrim, the cleanup card) is rounded with it (`Frame::round`), and the About window asks to be bigger by the shadow (`SHADOW_ROOM`). A desktop that decorates the window regardless (KDE) reports `Decorations::Server`, and the toolbar then sits under its title bar with no buttons and moves nothing. Whatever in a bar is something to press has to `occlude()`: that's what keeps a press on it from being a press on the bar. The About window has the same treatment, with only a close button, and all of it moves the window.

## Releases and updates

New versions come out as GitHub releases, from a `v*.*.*` tag (`.github/workflows/release.yaml`). The workflow checks the tag against the desktop crate's version, then builds the Mac app with `macos/build.sh` (signed and notarized when the Apple secrets are set, with the certificate imported from the `APPLE_CERTIFICATE`, a base64 .p12, and `APPLE_CERTIFICATE_PASSWORD` secrets; the `.dmg` and the `.zip`), the portable Windows build for x64 and arm64 (the exe in a zip; `src/desktop/build.rs` builds the icon into it as resource 1, which is also the one gpui gives the window and the taskbar) and the MSIX for each with `windows/build.ps1` (signed when the `WINDOWS_CERTIFICATE` and `WINDOWS_CERTIFICATE_PASSWORD` secrets are set, and otherwise the unsigned one, which goes on the GitHub release for trying the packaging but isn't in the bucket, `latest.json`, or the site's downloads, all of which go by the signed name; a step that's allowed to fail, so the rest of a release still goes out; the Store's package is still to come, and will be another one, signed by the Store), the portable Linux build for x64 and arm64 (the program in a zip, built on Ubuntu 22.04 to ask for an old C library; it can't be static, since it loads the system's GPU driver when it runs), and the Flatpak for x64 and arm64 (with the commit in `.commit`).

The publish job puts all of them on the GitHub release, and in a bucket, served at `releases.mckayla.dev/observatory`, the Mac zip at `darwin/arm64/`, the signed MSIXes (if there are any) at `win32/x64/` and `win32/arm64/`, and then `latest.json` (`no-cache`) naming them, which is all the app's updater reads. The builds go up before what points at them, and are cached for good. The job uploads with the AWS CLI (`--endpoint-url`, so any S3-compatible host), from the `RELEASES_BUCKET` / `RELEASES_ENDPOINT` / `RELEASES_REGION` variables and the `RELEASES_ACCESS_KEY_ID` / `RELEASES_SECRET_ACCESS_KEY` secrets, and is skipped until `RELEASES_BUCKET` is set. Every release goes in, prereleases too.

Started by hand (`workflow_dispatch`, on any branch), the workflow is a dry run: there's no tag to check, everything's built, signed, and packaged the same and can be downloaded from the run, and nothing's published. The run's summary lists what the release would have had and the `latest.json` it would have written. A dry run fails if the MSIX can't be made.

Updates are the app's own (`observatory_core::updates`, and `updating.rs` for the title bar's button). A copy that's an app, a bare program, or an MSIX installed by hand looks at launch and every hour: the bucket's `latest.json` (`{ version, url, downloads: { "darwin-arm64": <zip>, "win32-x64": <msix>, "win32-arm64": <msix> } }`), or if that can't be had, GitHub's list of the releases, where the build is the release's `Observatory-darwin-arm64-<version>.zip` or `Observatory-win32-<arch>-<version>.msix`. Anything newer gets "Version 1.2.0 is out", which opens the release's page. On macOS, an app that's signed with a certificate and sits somewhere writable goes further: it downloads the zip, checks it with `codesign` (whole, the same team as the running copy, Observatory, and the version it was told), and offers "Restart to update", which swaps the bundle and opens the new one. The team check is what the download is trusted by, since nobody who can write to the bucket or the releases can sign as that team; an ad hoc build has no team, and only gets the notice. On Windows, a copy that's an MSIX installed by hand gets the release's package when the notice is pressed ("Downloading 1.2.0…"): into the Downloads folder (a package's own AppData is a private copy nothing else can see), and then opened, so it's Windows' installer that checks its signature, asks, and updates the app. It trusts the package as it did the first one, by the certificate. The Store and Flatpak copies don't look at all: those update them. `OBSERVATORY_UPDATE_FEED` points a copy (a debug build too) at another feed, and `cargo run -p observatory-core --example update -- <version> [<app> <team>]` says what a copy of that version would find, and checks the download as that app would.

The site (`site/`) reads the latest release from GitHub when it's built (`release-plugin.ts`), so its download links name that release's files (the MSIX as Windows' installer, where the release has one): rebuild it after a release.
